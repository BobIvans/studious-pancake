# Новый чат: стратегия Web3/flashloan поверх уже существующего Studious Pancake
## Копировать этот запрос в начало новой стратегической сессии

Сначала получи самый свежий Repository/Operations Context Pack для `BobIvans/studious-pancake` и зафиксируй exact `repo_sha`, index generation и evidence generation. Используй доступ к GitHub/переданный pack; если pack отсутствует или stale, попроси coding agent обновить его, не делай вид, что видишь весь репозиторий.

До предложения любой новой стратегии:
1. Запроси из индекса полный компактный список существующих strategy ideas/implementations/versions, включая roadmap, research docs, code, configs, tests, PRs и paper/shadow episodes.
2. Для каждой связанной идеи раскрой точные entrypoint symbols, callers/callees, route/planner/compiler/simulator path, dependencies, data sources, provider/venue/pool, flash-capital source, configs, tests и известные outcomes.
3. Сравни новую гипотезу со всеми близкими existing nodes и выдай `DUPLICATE`, `EXTENSION` или `NOVEL` с доказательствами. Не предлагай повторно то, что уже есть под другим именем.
4. Разделяй `IDEA`, `IMPLEMENTED`, `WIRED`, `QUALIFIED`, `BLOCKED`, `RETIRED` и `UNKNOWN`. Документ, тестовый mock или имя класса сами по себе не подтверждают runtime capability.
5. Для внешних данных/инструментов проверь источник, timestamp/freshness, network/window, schema, license, quota, provenance и точные consumers.
6. Используй bounded retrieval: сначала не более 1,500 токенов обзорного pack, затем подтягивай только связанные graph subgraphs и exact source ranges по ссылкам. Не загружай весь репозиторий.
7. Для каждой новой стратегии укажи, что повторно используем, какие функции реально нужно добавить, какие данные нужны, какой отрицательный контроль и paper/shadow/replay test докажут гипотезу.
8. Выводы без источника помечай `UNKNOWN/NOT_OBSERVED`; не выдумывай исполнения, quotes, PnL или доступность источников.

Цель: итеративно улучшать весь существующий repo, не дублируя логику, данные, tools, стратегии и тесты. Любое изменение — через Task Packet, отдельный worktree/PR, тесты, Work Result Receipt и человеческий merge approval. LIVE остаётся hard-denied.
